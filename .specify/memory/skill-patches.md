# Project patches to the Spec Kit skills

The Spec Kit skills in `.claude/skills/speckit-*/SKILL.md` are generated by Spec Kit (hashes in
`.specify/integrations/claude.manifest.json`). Three are patched so they follow the change-spec
format of constitution v2.4.0; an upgrade of Spec Kit will overwrite them, so re-apply these
patches afterwards. Each patched place is marked "Project patch" in the skill.

The templates themselves are overridden without patching anything, in
`.specify/templates/overrides/` (spec, plan, tasks).

| Skill | What changes | Why |
|---|---|---|
| `speckit-specify` | Execution flow steps 4–7: read the capabilities touched, write added / changed / removed rules with ids, write acceptance scenarios from the demo data and check them, note demo data changes and out of scope (instead of user scenarios, functional requirements, success criteria, key entities). Quality checklist items: no history, rule ids and who/what/when, rules once, quoted UI texts, decisions, scenarios per rule, names and counts against the demo data. "Document assumptions" → Decisions. "Success Criteria Guidelines" → "Acceptance Scenario Guidelines". | The spec is a change to capabilities; it has no user stories or success criteria |
| `speckit-plan` | Phase 0: skip `research.md` when there is no non-obvious decision. Phase 1: `data-model.md` only for data shapes that change, `contracts/` only when screens or routes change, `quickstart.md` refers to the spec's acceptance scenarios instead of copying them. | Avoid empty or duplicated artifacts |
| `speckit-tasks` | Organize tasks by rule groups instead of user stories; task format ends with the rule ids instead of a `[US#]` label; test tasks for every pure rule (constitution III, instead of "tests optional"); phases Rules → rule groups → "Apply the change to the capabilities" → "Checks"; completion report per phase. | The spec has no user stories; the closing phase keeps the capability files true |

Patched on 2026-10-26 against Spec Kit 1.2.4.dev0.
